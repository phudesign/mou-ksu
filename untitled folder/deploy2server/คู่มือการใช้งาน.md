## 1. ภาพรวม

`deploy2server/` เป็น**แพ็กเกจครบในตัว** สำหรับขึ้นเซิร์ฟเวอร์:

- โค้ด backend + frontend static (`html/` + Dockerfile)
- ไฟล์ Kubernetes / OpenShift (Deployment, Service, Route, MySQL)
- ฐานข้อมูล (schema, seed, dump ข้อมูลเต็ม, ไฟล์ uploads)
- สคริปต์ build / push / deploy / import ข้อมูล

```text
เครื่องพัฒนา                Registry              Kubernetes (เซิร์ฟเวอร์)
─────────────              ────────              ─────────────────────
แก้โค้ด ──sync──► build/ ──build-push──► images ──deploy──► Pods ใน namespace
export-data ──► database/ ────────────────────── import-data ──► MySQL + uploads
```

**สมมติฐานสำคัญ:** Admin สร้าง **namespace** ให้แล้ว (สคริปต์จะไม่สร้าง namespace ใหม่)

ทดลองในเครื่องด้วย Docker Desktop ใช้โฟลเดอร์ `k8s/` ของ repo หลัก (`npm run k8s:up`) คนละชุดกับคู่มือนี้

## 2. สิ่งที่ต้องมีก่อนเริ่ม

### 2.1 ขอจาก Admin / ทีม Infra

| รายการ | ตัวอย่าง | ใส่ที่ไหน |
|--------|----------|----------|
| ชื่อ namespace | `mou` | `config.env` → `NAMESPACE` |
| สิทธิ์ kubectl ใน namespace | kubeconfig | เครื่องที่รันสคริปต์ |
| URL Container Registry | `registry.example.com/mou` | `REGISTRY` |
| วิธี login registry | username/password หรือ token | `docker login` |
| imagePullSecret (ถ้ารegistry ปิด) | `regcred` | `IMAGE_PULL_SECRET` |
| โดเมนเว็บ (Route host) | `mou.ksu.ac.th` | `INGRESS_HOST` |
| StorageClass (ถ้ามี) | `standard` | `STORAGE_CLASS` |
| ใช้ TLS ที่ Route หรือไม่ | edge ผ่าน OpenShift Router | `ENABLE_TLS` |

ตรวจว่าเข้าคลัสเตอร์และเห็น namespaceได้:

```bash
kubectl config current-context
kubectl get ns
kubectl -n <NAMESPACE> auth can-i create deployments
```

### 2.2 ซอฟต์แวร์บนเครื่องที่ build / deploy

- Docker (สำหรับ `build-push`)
- `kubectl` ชี้ไปคลัสเตอร์จริง
- เครือข่ายถึง registry และ API ของคลัสเตอร์
- (ถ้า export จากเครื่องพัฒนา) Docker Compose หรือ K8s local ที่มีข้อมูล

### 2.3 ค่าลับที่ต้องเตรียมเอง

ใน `k8s/secret.yaml` (สร้างจากตัวอย่าง):

- `DB_PASS` — รหัส MySQL แข็งแรง
- `JWT_SECRET` — สุ่มอย่างน้อย 32 ตัวอักษร (ของ production ใหม่)
- `LDAP_AUTH_API_TOKEN` — token จากระบบ LDAP จริง

อย่า commit หรือส่งไฟล์นี้ทางแชทสาธารณะ

## 4. ส่วนที่ 1 — เริ่มใช้งานครั้งแรก

ทำตามลำดับนี้ตั้งแต่ต้นจนเว็บใช้งานได้

### ขั้นที่ 1 — เตรียมแพ็กเกจบนเครื่องพัฒนา (แนะนำ)

ถ้า `deploy2server` ยังอยู่ใน repo โปรเจกต์:

```bash
# จาก root ของโปรเจกต์
./deploy2server/scripts/sync-from-repo.sh
./deploy2server/scripts/export-data.sh
```

- `sync-from-repo` อัปเดต `build/backend`, `build/frontend`, schema/seed  
- `export-data` สร้าง/รีเฟรช `database/data/mou_db_full.sql` และ `database/uploads/`

จากนั้น**คัดลอกทั้งโฟลเดอร์ `deploy2server/`** ไปเครื่องที่ login registry และ `kubectl` ไปคลัสเตอร์จริงได้  
(ถ้าเครื่องพัฒนาทำได้ทั้งสองอย่าง ข้ามการคัดลอกได้)

### ขั้นที่ 2 — สร้างไฟล์ตั้งค่า

```bash
cd deploy2server
cp config.env.example config.env
cp k8s/secret.example.yaml k8s/secret.yaml
```

#### แก้ `config.env` (ตัวอย่าง)

```bash
NAMESPACE=mou
REGISTRY=registry.example.com/mou
IMAGE_TAG=1.0.0
INGRESS_HOST=mou.example.com
CORS_ORIGIN=https://mou.example.com
ENABLE_TLS=false
STORAGE_CLASS=
IMAGE_PULL_SECRET=
```

คำอธิบายสั้นๆ:

| ตัวแปร | ความหมาย |
|--------|----------|
| `NAMESPACE` | ต้องตรงที่ admin สร้างให้ |
| `REGISTRY` | ไม่มี `/` ท้าย — image จะเป็น `{REGISTRY}/backend:{TAG}` |
| `IMAGE_TAG` | เวอร์ชัน เช่น `1.0.0` หรือ `20261028` |
| `INGRESS_HOST` | โดเมนใน OpenShift Route (`spec.host`) |
| `CORS_ORIGIN` | โดยปกติ `https://` + โดเมนเดียวกับด้านบน |
| `ENABLE_TLS` | `true` = Route แบบ edge + redirect HTTP→HTTPS |
| `BACKEND_CONTEXT` / `WEB_CONTEXT` | ค่าเริ่มต้นชี้ `./build/...` อยู่แล้ว |

#### แก้ `k8s/secret.yaml`

```yaml
stringData:
  DB_USER: root
  DB_PASS: <รหัสแข็งแรง>
  DB_NAME: mou_db
  JWT_SECRET: <สุ่มยาวอย่างน้อย 32 ตัว>
  LDAP_AUTH_API_TOKEN: "<token จริง>"
```

บรรทัด `namespace: __NAMESPACE__` **อย่าลบ** — สคริปต์จะแทนที่ตาม `config.env`

### ขั้นที่ 3 — (ทางเลือก) ดูไฟล์ก่อน apply

```bash
./scripts/render.sh
ls .generated/
```

ตรวจว่า image, namespace, host ถูกต้องใน `.generated/*.yaml`

### ขั้นที่ 4 — Login registry แล้ว Build + Push

```bash
docker login registry.example.com
./scripts/build-push.sh
```

สิ่งที่เกิดขึ้น:

1. `docker build` จาก `build/backend` → push `{REGISTRY}/backend:{IMAGE_TAG}`  
2. `docker build` จาก `build/frontend` (Nginx + `html/` ที่ sync มาแล้ว) → push `{REGISTRY}/web:{IMAGE_TAG}`

`sync-from-repo.sh` จะ build Flutter บนเครื่องพัฒนา (`API_URL=same-origin`) แล้วใส่ไฟล์ใน `build/frontend/html/` — Docker แค่แพ็ก static ไม่ต้องมี Flutter SDK

### ขั้นที่ 5 — Deploy ลง namespace

```bash
./scripts/deploy.sh
```

สคริปต์จะ:

1. ตรวจว่า namespace มีอยู่  
2. apply Secret, ConfigMap (schema/seed), MySQL, backend, web, Route  
3. รอจน Deployment Ready  

ดูสถานะ:

```bash
./scripts/status.sh
```

ควรเห็น pod `mysql`, `backend`, `web` เป็น `Running`

### ขั้นที่ 6 — นำข้อมูลเต็มเข้าเซิร์ฟเวอร์

ตอน deploy ครั้งแรก MySQL จะได้แค่ schema + seed เล็กน้อย  
ต้อง import dump เต็ม + ไฟล์ uploads:

```bash
./scripts/import-data.sh
```

พิมพ์ `yes` เพื่อยืนยัน  
**คำเตือน:** คำสั่งนี้**ทับข้อมูลทั้งหมด**ใน `mou_db` ของ namespace นั้น

### ขั้นที่ 7 — ตรวจสอบว่าใช้งานได้

```bash
curl -i https://<INGRESS_HOST>/
curl -i https://<INGRESS_HOST>/api/health
```

เปิดเบราว์เซอร์ที่โดเมนจริง แล้วลอง:

1. หน้า login โหลดได้  
2. Login ด้วย LDAP ได้  
3. เห็นรายการเอกสาร (ถ้า import ข้อมูลแล้ว)  
4. เปิดเอกสาร / เซ็น (ทดสอบ Socket.IO)

## 5. ส่วนที่ 2 — อัปเดตโค้ด

ใช้เมื่อแก้ backend หรือ frontend แล้วอยากขึ้นเซิร์ฟเวอร์โดย**ไม่ต้องลบฐานข้อมูล**

### 5.1 กรณีแก้ใน repo หลัก (แนะนำ)

```text
1. แก้โค้ดใน backend/ หรือ flutter_mou/
2. sync เข้า deploy2server/build/
3. เปลี่ยน IMAGE_TAG (สำคัญ)
4. build-push
5. deploy ใหม่
```

#### ทีละคำสั่ง

```bash
# บนเครื่องที่มี repo เต็ม
./deploy2server/scripts/sync-from-repo.sh

# แก้ IMAGE_TAG ใน deploy2server/config.env เช่น จาก 1.0.0 → 1.0.1
# เปิดไฟล์แล้วเปลี่ยน IMAGE_TAG=1.0.1

./deploy2server/scripts/build-push.sh
./deploy2server/scripts/deploy.sh
./deploy2server/scripts/status.sh
```

หรือจาก root repo:

```bash
npm run deploy:sync
# แก้ IMAGE_TAG ใน deploy2server/config.env
npm run deploy:build-push
npm run deploy:apply
npm run deploy:status
```

### 5.2 ทำไมต้องเปลี่ยน IMAGE_TAG

ถ้าใช้แท็กเดิม (เช่น `1.0.0` ซ้ำ) บางคลัสเตอร์อาจยังดึง image เก่าจาก cache  
เปลี่ยนแท็กทุกครั้งที่ปล่อยของใหม่ จะชัวร์กว่า เช่น:

- `1.0.1`, `1.0.2`, …
- หรือวันที่ `20261028-01`

ใน Deployment ตั้ง `imagePullPolicy: Always` อยู่แล้ว แต่แท็กใหม่ยังเป็นนิสัยที่ดี

### 5.3 อัปเดตเฉพาะ backend หรือเฉพาะ frontend

สคริปต์ `build-push.sh` build ทั้งคู่  
ถ้าต้องการแยกด้วยมือ:

```bash
# โหลด config ก่อน หรือใส่ค่าเอง
source <(grep -v '^#' config.env | grep -v '^$')

docker build -t "${REGISTRY}/backend:${IMAGE_TAG}" ./build/backend
docker push "${REGISTRY}/backend:${IMAGE_TAG}"

docker build -t "${REGISTRY}/web:${IMAGE_TAG}" ./build/frontend
docker push "${REGISTRY}/web:${IMAGE_TAG}"
```

จากนั้น `./scripts/deploy.sh` (หรือ `kubectl set image` / rollout restart หลังแก้ tag ใน manifest ผ่าน deploy)

### 5.4 แก้โค้ดตรงใน `deploy2server/build/` บนเครื่อง deploy

ถ้าไม่มี repo เต็มบนเครื่องนั้น:

1. แก้ไฟล์ใน `build/backend` หรือ `build/frontend`  
2. เปลี่ยน `IMAGE_TAG`  
3. `./scripts/build-push.sh`  
4. `./scripts/deploy.sh`  

ไม่ต้องรัน `sync-from-repo.sh`

### 5.5 สิ่งที่อัปเดตโค้ด**ไม่**ทำให้อัตโนมัติ

| รายการ | ต้องทำแยกไหม |
|--------|----------------|
| ข้อมูลใน MySQL | ไม่ถูกลบเมื่อ deploy ใหม่ (PVC เดิม) |
| ไฟล์ uploads บน PVC | คงอยู่ |
| Secret / LDAP token | คงอยู่ เว้นแต่คุณ apply secret ใหม่ |
| schema ตารางใหม่ | ถ้ามี migration ต้องรัน SQL เอง (ดูส่วนที่ 3) |

### 5.6 Rollback เวอร์ชันเก่า (แนวทาง)

1. ตั้ง `IMAGE_TAG` กลับเป็นแท็กที่เคย push ไว้  
2. `./scripts/deploy.sh`  

หรือ:

```bash
kubectl -n <NAMESPACE> rollout undo deploy/backend
kubectl -n <NAMESPACE> rollout undo deploy/web
```

(undo ใช้ประวัติ ReplicaSet ในคลัสเตอร์ — ใช้ได้ถ้ายังไม่ลบ revision เก่า)

## 6. ส่วนที่ 3 — อัปเดตข้อมูลฐานข้อมูล

รายละเอียดเต็มอยู่ที่ `database/README.md` — สรุปที่นี่เพื่อให้ครบในคู่มือเดียว

### 6.1 ส่งข้อมูลจากเครื่องพัฒนาเข้าแพ็กเกจ

```bash
./scripts/export-data.sh
```

ได้:

- `database/data/mou_db_full.sql`
- `database/uploads/`
- `database/data/EXPORT_INFO.txt` (จำนวนแถว / เวลา)

### 6.2 นำข้อมูลเต็มขึ้นเซิร์ฟเวอร์ (ทับของเดิม)

```bash
./scripts/import-data.sh
# พิมพ์ yes
```

**บน production ที่มีผู้ใช้จริง:** สำรองก่อนเสมอ

```bash
./scripts/backup-db.sh
./scripts/import-data.sh
```

### 6.3 แค่อัปเดตโครงสร้างตาราง (ไม่ทับ dump)

```bash
./scripts/import-schema-only.sh
# หรือพร้อม seed เล็กน้อย:
./scripts/import-schema-only.sh --with-seed
```

`schema.sql` ใช้ `CREATE TABLE IF NOT EXISTS` เป็นหลัก — ไม่ลบแถวเดิม แต่**ไม่แทนที่คอลัมน์ที่เปลี่ยนแบบซับซ้อน**  
ถ้ามี migration เฉพาะ ควรรัน SQL ที่ออกแบบมาเอง

### 6.4 ตารางเปรียบเทียบ

| เป้าหมาย | คำสั่ง | ทับข้อมูลไหม |
|----------|--------|----------------|
| ย้ายข้อมูลทั้งก้อน + ไฟล์ | `import-data.sh` | ใช่ |
| เพิ่มตารางตาม schema | `import-schema-only.sh` | ไม่ (โดยทั่วไป) |
| สำรองจากเซิร์ฟเวอร์ | `backup-db.sh` | ไม่ |
| รีเฟรช dump ในแพ็กเกจ | `export-data.sh` | ไม่กระทบเซิร์ฟเวอร์ |

## 7. คำสั่งอ้างอิงทั้งหมด

รันจากโฟลเดอร์ `deploy2server/` เว้นแต่ระบุว่าจาก root repo

| งาน | คำสั่ง |
|-----|--------|
| ซิงก์โค้ดจาก repo | `./scripts/sync-from-repo.sh` หรือ `npm run deploy:sync` |
| Export DB+uploads เข้าแพ็กเกจ | `./scripts/export-data.sh` หรือ `npm run deploy:export-data` |
| เรนเดอร์ YAML ดูอย่างเดียว | `./scripts/render.sh` |
| Build + push image | `./scripts/build-push.sh` หรือ `npm run deploy:build-push` |
| Deploy / apply | `./scripts/deploy.sh` หรือ `npm run deploy:apply` |
| สถานะ | `./scripts/status.sh` หรือ `npm run deploy:status` |
| Import ข้อมูลเต็ม | `./scripts/import-data.sh` หรือ `npm run deploy:import-data` |
| Import แค่ schema | `./scripts/import-schema-only.sh` |
| Backup DB บนเซิร์ฟเวอร์ | `./scripts/backup-db.sh` หรือ `npm run deploy:backup-db` |

## 8. ตรวจสุขภาพระบบ / ดู log

```bash
# สถานะรวม
./scripts/status.sh

# Log
kubectl -n <NAMESPACE> logs -f deploy/backend
kubectl -n <NAMESPACE> logs -f deploy/web
kubectl -n <NAMESPACE> logs -f deploy/mysql

# อธิบาย pod ที่ไม่ Ready
kubectl -n <NAMESPACE> describe pod -l app=backend
kubectl -n <NAMESPACE> get events --sort-by=.lastTimestamp | tail -30

# Health ผ่านโดเมน
curl -i https://<INGRESS_HOST>/api/health
```

เข้า MySQL ในคลัสเตอร์ (ระวังรหัสผ่าน):

```bash
kubectl -n <NAMESPACE> exec -it deploy/mysql -- mysql -uroot -p mou_db
```

## 9. แก้ปัญหาที่พบบ่อย

| อาการ | สาเหตุที่เป็นไปได้ | วิธีแก้ |
|--------|-------------------|--------|
| `ไม่พบ namespace` | ชื่อใน config ผิด / ยังไม่มี ns | แก้ `NAMESPACE` หรือให้ admin สร้าง |
| `ImagePullBackOff` | ยังไม่ push / login ไม่ได้ / ไม่มี pull secret | `docker login`, ตรวจ `IMAGE_PULL_SECRET`, ชื่อ image |
| Route ไม่เข้า | DNS / host ไม่อนุญาต / Router | ถาม admin เรื่องโดเมน Route และ DNS |
| Login ได้ 503 Authentication service unavailable | LDAP token ว่างหรือผิด | แก้ `secret.yaml` แล้ว `kubectl apply` + rollout restart backend |
| Login 401 | username/password หรือยังไม่อยู่ในตาราง users | ตรวจ LDAP และตาราง `users` |
| เอกสารไม่มีไฟล์ PDF | ยังไม่ import uploads | รัน `import-data.sh` หรือคัดลอก uploads เอง |
| แก้โค้ดแล้วไม่เห็นของใหม่ | ใช้ `IMAGE_TAG` เดิม | เปลี่ยนแท็ก แล้ว build-push + deploy |
| PVC Pending | ไม่มี StorageClass | ตั้ง `STORAGE_CLASS` ตามที่ admin บอก |

รีสตาร์ท backend หลังแก้ Secret:

```bash
kubectl apply -f .generated/secret.yaml   # หรือรัน deploy.sh อีกครั้ง
kubectl -n <NAMESPACE> rollout restart deploy/backend
kubectl -n <NAMESPACE> rollout status deploy/backend
```

## 10. สิ่งที่ห้ามทำ

1. **อย่า commit** `config.env`, `k8s/secret.yaml`, `.generated/`, `backups/`  
2. **อย่าใช้** `npm run k8s:down` ของเครื่องทดลองกับคลัสเตอร์จริง (คนละชุดสคริปต์อยู่แล้ว แต่ระวัง context ของ kubectl)  
3. **ตรวจ** `kubectl config current-context` ทุกครั้งก่อน deploy / import  
4. **อย่า** `import-data.sh` บน production โดยไม่ backup ถ้ามีข้อมูลผู้ใช้จริงแล้ว  
5. **อย่าแชร์** LDAP token / JWT / รหัส DB ในแชทหรือ ticket สาธารณะ  

ก่อนคำสั่งสำคัญ:

```bash
kubectl config current-context
echo "NAMESPACE ใน config.env ต้องตรงกับที่ตั้งใจ"
```
